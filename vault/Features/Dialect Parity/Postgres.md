# PostgreSQL — Dialect Parity Inventory

## Summary

Benchmarks against the `psql` command-line client shipped with PostgreSQL 15+ (compatible with 13+ where noted). Covers the meta-command and SQL feature surface a seasoned Postgres DBA expects when they sit down at a shell — what's implemented, what's pending, and what's explicitly blocked by the browser boundary or by design.

**Interview complete.** Both axes walked:

- **Axis 1** — meta-commands — nine categories walked across Rounds 1–9. ~260 rows catalogued.
- **Axis 2** — SQL dialect features — vendor-specific surface identified across Round 10. ~50 rows consolidated into a single keyword/function-list audit work item, one Postgres-specific operator-table polish item, and cross-plane UX hooks with Postgres-specific variants.

**Tier totals across both axes:**

| Tier | Count | Meaning |
|:---:|:---:|---|
| T1 | ~180 | Implemented today, or trivial SQL passthrough. |
| T2 | ~60 | Pending infrastructure. Heavier than MySQL's count because every missing `\d*` meta-command is plane work — ~28 catalog-query translations alone, best-delivered as a single one-pass sprint (Track 7 below). |
| T3 | ~12 | Individual engineering items — each needs its own design pass. Includes the Plan Viewer pane (cross-plane peer of MySQL's), Permissions Explorer pane (richer for Postgres because RLS + default privs + role graph), `\copy` FROM/TO, dollar-quote-aware statement splitter, Large Object family, `\if` family, `\gexec`, Activity-pane Explain hook (harder than MySQL due to no `EXPLAIN FOR CONNECTION`). |
| BL | ~8 | Blocked by the browser sandbox, will lift when [[OS Provider Seam]] implementations ship. |
| BD | ~2 | Blocked by design — not planned for implementation. OS shell escape (`\!`), external pager (`\pset pager`). Mostly cross-plane cross-refs from MySQL Round 2. (External editor moved out of BD on 2026-10-01 — see the `\e` row.) |
| Out of scope / legacy | ~15 | Explicit skips documented per row; aggregated in [the Out of scope section](#out-of-scope) at the bottom of this doc. |

**Framework:** [[Dialect Coverage Framework]]. Tier scheme, runtime grace contract (`NotYetImplemented` / `NotSupported`), and inventory doc shape all defined there. This doc follows that shape.

**Family variant policy** — Aurora Postgres, Citus-extended Postgres, YugabyteDB, CockroachDB, and other Postgres-wire-compatible engines get their own inventory docs when we formally support them. See [[README|the parity README]] for the "no cross-dialect borrowing" policy and the broader family policy.

**Key structural difference from MySQL.** Postgres's native CLI is `psql`, which is **much more meta-command-heavy** than `mysql`. Where MySQL exposes metadata via `SHOW` (SQL passthrough), Postgres exposes it via `\dt` / `\dv` / `\df` / `\d` (client-side backslash commands that `psql` translates internally into `SELECT ... FROM pg_catalog`). Our job is to replicate those translations in `PostgresPlane::meta_cmd` — so nearly every Postgres row in the inventory involves plane work, not passthrough. **Postgres's Axis 1 tier distribution leans T2 where MySQL's leaned T1.**

- Sections under **Meta-commands (Axis 1)** are ordered by the canonical category list from the framework (Metadata → Session Control → Scripting → Query Planning → Monitoring & Replication → File I/O → Admin → Auth → Shell Interaction). The interview that populated them ran the categories in a different order; each section notes the round that walked it.
- Sections under **SQL dialect features (Axis 2)** are ordered by SQL layer (DQL / DML / DDL / DCL / TCL / Session-admin / Procedural).
- Every row has `Command`, `Aliases`, `Status`, `Tier`, and `Notes`. The framework's tier definitions are canonical; specific per-row caveats live in the notes.
- **Browser limitations** and **Out of scope** sections at the bottom consolidate every BL / BD / OOS row across every category into one scannable table each.
- Every `[[link]]` is a wiki-style reference to another vault doc. Verified consistent as of the consolidation pass.
- **Cross-plane work shared with MySQL** is not re-catalogued here; the Implementation Tracks section below cross-refs the MySQL-originated tracks and only lists Postgres-specific adjustments. Readers hunting for shell-level features (persistent history, Ctrl+R, readline keys, tab completion, `\help <cmd>`, `\safe-mode`, `\output` toggle) should read the tracks here *and* [[MySQL#Implementation tracks]].

## Implementation tracks

Cross-cutting work streams for Postgres. Most tracks are **cross-plane extensions** of the tracks originated in [[MySQL#Implementation tracks]] — one design doc + one implementation pass lights up both planes. Postgres surfaces two new tracks (one sprint-able catalog-query block, one operator-highlighting polish).

### Track 1 — Shell rendering polish (cross-plane, extended)

Same six items as MySQL Track 1. Postgres additions:

- **Grant-cards renderer** (originated MySQL Round 8) now also handles **default privileges** (Round 8 — Postgres `ALTER DEFAULT PRIVILEGES`) and **RLS policies** (Round 8 — `CREATE POLICY`) as distinct card categories. Three categories: default privs, current privs, column privs. RLS policies as a separate card style.
- **Wide-result auto-vertical rendering** (originated MySQL Round 5) should default to **`auto` mode** per Postgres `\pset expanded auto` — least-surprising shape for Postgres DBAs. `\pset expanded auto` (PG 9.5+) is essentially the native feature we're trying to match.
- **Long-text result rendering** covers Postgres's EXPLAIN TEXT / EXPLAIN ANALYZE output the same way it covers MySQL's TREE format.

### Track 2 — Shell-layer SQL intercept (cross-plane, extended)

Same six items as MySQL Track 2. Postgres adds two variants on existing items:

- **Transaction-state indicator** (Track 2 item 5) adds a **"failed transaction" sub-state** (distinct colour) for Postgres's aborted-transaction case — inside a failed Postgres transaction, every subsequent statement except ROLLBACK errors with "current transaction is aborted". MySQL has no direct equivalent.
- **Schema-cache invalidation on DDL** (Track 2 item 6) adds **rollback-aware triggering** — Postgres's DDL inside a transaction can be undone by ROLLBACK, so invalidation fires on both the DDL statement AND the subsequent commit/rollback.
- **`\safe-mode`** uses Postgres-specific `destructive_patterns()`: `DROP DATABASE`, `DROP SCHEMA`, `DROP TABLE`, `TRUNCATE`, `DROP ROLE`, `DROP USER`, `DROP TABLESPACE`, `DROP OWNED BY` (8 patterns). Different from MySQL's 10-pattern list — no SQL `SHUTDOWN` / `RESET MASTER` in Postgres; Postgres-only `DROP OWNED BY` is added.
- **Advisory pattern** lights up for Postgres server-side `COPY FROM/TO 'path'` (wrong-filesystem warning), bare `COPY FROM STDIN` (nudges to `\copy`), and `ALTER SYSTEM SET` (persistence warning — future safe-mode candidate).

### Track 3 — `BrowserOsProvider` consumers (cross-plane, extended)

Same five items as MySQL Track 3, with Postgres additions:

1. **`\i filename` / `\ir filename`** (Round 3) — Postgres equivalent of MySQL's `SOURCE`. Same infrastructure. First Phase-1 parity item per [[OS Provider Seam]].
2. **"Save result as..." download action** — shared with MySQL Track 3 item 2.
3. **`\o filename` tee** (Round 6) — Postgres-specific but shares `BrowserOsProvider::write_download` plumbing. Semantically differs from MySQL's `\T` (replace vs duplicate output).
4. **`\s filename` save history** (Round 9) — write persistent history to a file. Trivial once persistent-history infrastructure exists.
5. **`\w filename` write query buffer** (Round 6, low priority) — write the current input textarea to a file.
6. **`\copy FROM/TO 'filename'`** (Round 6) — **T3 + BL, not spike-deferred.** sqlx's Postgres COPY API is mature; real v0.0.2 work. **Not parked the way MySQL's LOAD DATA LOCAL INFILE is.**
7. **Drag-and-drop file attach** — shared with MySQL Track 3 item 4 (deprioritized both sides).
8. **Large Object family** (`\lo_import` / `\lo_export`) — T3 niche. Deferred until user demand; bundled together.

### Track 4 — Cross-plane shell features (cross-plane, unchanged)

Same five items as MySQL Track 4 (persistent history, Ctrl+R, readline keybindings, tab completion, `\help <cmd>`). All shared across planes. Postgres adds:

- **`\set` / `:var` / `\unset` / `\prompt`** (Round 2) — psql's client-side variable substitution. Native psql feature; cross-plane T2 infrastructure that MySQL's side can adopt too (`\set` pattern) if ever wanted. Plus tab-completion on `\set` variable names rolls in.
- **`\watch [seconds]`** (Round 5) — native psql auto-repeat. T1 — wires to the Activity pane's existing `Timer::register_fn` infrastructure. Cross-plane candidate — MySQL has no analog but could copy it as parity-plus.
- **`\h KEYWORD` local SQL syntax help database** (Round 9) — T2 with a bundled data payload (~500 topics compiled from PG 16 SGML docs). Plane-specific (MySQL has the server-side `help 'SELECT'` path from `mysql.help_topic`).

### Track 5 — New pane types (cross-plane, extended)

Same three items as MySQL Track 5, with Postgres deltas:

1. **Plan Viewer pane** (Round 4) — **plane-aware from day one.** Postgres is a peer of MySQL in the pane, not a follow-up. Different node types (Seq Scan / Hash Join / Gather / …) render through a `DbmsPlane::plan_renderer()` hook distinct from MySQL's tree shape. Shared pane shell (Raw JSON / Readable Text / Graphical Tree tab strip); plane-specific tree-walker implementations. Design doc addresses both dialects together.
2. **Permissions Explorer pane** (Round 8) — **richer for Postgres than for MySQL.** RLS policies, default privileges, and explicit role-graph all deserve first-class views (via `pg_auth_members`). Same pane type; plane-specific data sources.
3. **Activity-pane Replication sub-view** (Round 5) — deferred on both sides. Postgres's logical-replication surface is arguably more first-class (publications / subscriptions as visible objects); if we ever build this, Postgres gets a richer view. Still deferred until real user demand.

### Track 6 — Keyword / function / operator list audit (consolidated)

Single work item: "audit + expand `POSTGRES_KEYWORDS`, `POSTGRES_FUNCTIONS`, and `POSTGRES_OPERATORS` in `tyto/src/plane/postgres.rs` against the PostgreSQL 16 reference manual." Covers the ~50 T1-polish rows from Round 10's Axis 2 walk — DQL (CTEs materialized variants, window frame modes, DISTINCT ON, LATERAL, FILTER, FETCH FIRST WITH TIES, GROUPING SETS, ROLLUP, CUBE, WITH ORDINALITY), DML (ON CONFLICT, RETURNING, UPDATE FROM, DELETE USING, MERGE), DDL (inheritance, partitioning, IDENTITY columns, exclusion constraints, index access methods, CREATE TYPE/DOMAIN/EXTENSION/FDW/EVENT TRIGGER/STATISTICS), TCL (DEFERRABLE transactions, SET TRANSACTION SNAPSHOT, PREPARE TRANSACTION), and PL/pgSQL procedural (~80 keywords — DECLARE/BEGIN/END/IF/ELSIF/CASE/LOOP/WHILE/FOR/FOREACH/EXIT/CONTINUE/RAISE/EXCEPTION/RETURN NEXT/RETURN QUERY/PERFORM/GET DIAGNOSTICS/…).

### Track 7 — Postgres metadata catalog sprint (Postgres-only, NEW)

**The single biggest concrete-work item for Postgres parity.** ~28 `\d*` meta-commands pending in Round 1 (Metadata & Introspection), each needing a `SELECT ... FROM pg_catalog.*` translation in `PostgresPlane::meta_cmd`. Per-item work is small and repetitive — single design pattern, many instances. **One-pass sprint with shared scaffolding** (pattern-match helper, `+` variant verbose-column extender, shared `S` system-object filter toggle) rather than 28 individual tickets.

Items in the sprint:

- List-style: `\dm` / `\ds` / `\di` / `\dT` / `\da` / `\dc` / `\dC` / `\dD` / `\dL` / `\dO` / `\dF` / `\dFd` / `\dFp` / `\dFt` / `\dx` / `\dy` / `\dP` / `\dPi` / `\dPt` / `\dRp` / `\dRs` / `\dE` / `\des` / `\deu` / `\dew` / `\dl` / `\drg` (PG 16+) / `\ddp` / `\dp` / `\z`
- `\df` variants: `\dfa` / `\dfn` / `\dft` / `\dfw`
- `\d+` verbose extension (existing `\d` composite with indexes / constraints / triggers / rules)
- `\l+` (size / tablespace / description extension)
- `\sf` / `\sv` / `\ef` / `\ev` (show/edit function/view — already have internal queries from Schema Explorer)
- `\conninfo` and `\dconfig` (cross-cutting; could be included or split off as T1 quick wins)

All share the same plane-layer shape. Sprint candidate for v0.0.2; two `\d*` quick wins (`\conninfo`, `\dconfig`) can ship earlier as T1/T2 standalones.

### Track 8 — Operator highlighter polish (Postgres-surfaced, cross-plane infra)

**Surfaced from Round 10 Axis 2.** Postgres is heavily operator-reliant — JSON (`->`, `->>`, `#>`, `@>`, `?`, `?|`, `?&`, `@@`, `@?`), range (`<<`, `>>`, `-|-`, `*`), geometric (`##`, `<->`, `?#`, `?-`), regex (`~`, `~*`, `!~`, `!~*`), text-search (`@@`). Current highlighter renders operators as plain punctuation. **Add an operator-table extension to the plane's `highlight.rs` tokenizer** so operators render distinctly from identifiers and punctuation. Single infrastructure change; lights up ~40 Postgres operators. Infrastructure is cross-plane (plane-driven operator table); MySQL has a smaller but non-zero operator surface (`->` / `->>` JSON operators — already covered partially) that adopts it too.

**Round 1 summary:**

- 40 rows catalogued. **The first T2-heavy round** — 28 T2 items because each missing `\d*` command needs a plane translation.
- **`\conninfo` shipped** as a T1 quick win.
- **The `\d*` family dominates the remaining T2 queue.** Implementation is repetitive: each command adds a match arm to `PostgresPlane::meta_cmd` that returns a `SELECT ... FROM pg_catalog.*` query. ### Scripting

**Two substantive Postgres-specific items** beyond what MySQL's scripting round covered:

1. **Dollar-quoted strings (`$$ ... $$`, `$tag$ ... $tag$`)** — Postgres's preferred quoting for function bodies, DO blocks, triggers. The multi-statement parser **must** handle these correctly or function definitions break silently (it splits on a `;` inside a function body). **Promotes the parser from T2 → T3 for the Postgres plane** because nested tags and arbitrary tag names make tokenization non-trivial.

2. **`\if` / `\elif` / `\else` / `\endif` script control flow** — Postgres has client-side conditional execution in psql. No MySQL analog: a MySQL shell leaves them to the mysql CLI's own reading (`\if` is its unknown `\i` — see the MySQL doc). Implemented as psql's conditional stack (`psql_if`), kept on the shell across Enters, each branching command applied where it stands as the input is read in order (2026-10-12).

### Query Planning

Postgres's planner surface is **richer than MySQL's** — `EXPLAIN` has more output formats (`TEXT` / `XML` / `JSON` / `YAML`), more modifiers (`VERBOSE` / `COSTS` / `BUFFERS` / `WAL` / `TIMING` / `SUMMARY` / `SETTINGS` / `GENERIC_PLAN`), and a genuinely different plan-tree shape (Seq Scan / Index Scan / Bitmap Heap Scan / Nested Loop / Hash Join / Merge Join / Sort / Aggregate / Gather / …). All SQL passthrough — the planner is server-side.

**Two key decisions cross-ref MySQL Round 4:**

1. **Plan Viewer pane is plane-aware, not MySQL-only.** The `PaneKind::PlanViewer` work planned in MySQL Round 4 lands with plane-specific rendering primitives from day one: Postgres's node types (Seq Scan, Hash Join, Gather, etc.) render through a `DbmsPlane::plan_renderer()` hook that produces the Readable Text and Graphical Tree views. MySQL's JSON plan and Postgres's JSON plan share the same pane shell (tab strip, three views) but different tree-walker implementations. Design the pane with this split in mind from the first sketch.
2. **Activity pane "Explain this query" hook is T3 for Postgres** — harder than MySQL because Postgres has **no `EXPLAIN FOR CONNECTION N` equivalent.** The workflow is: pull `query` text from `pg_stat_activity` for the target pid, open a new shell / Plan Viewer on the same connection, run `EXPLAIN (FORMAT JSON) <query>`. Different session → different plan (no guarantee it matches the running one's actual plan), but it's the closest Postgres offers. Flag this capability gap explicitly.

### File I/O

Postgres's file-I/O surface is **smaller and cleaner** than MySQL's — one client-side file-transfer command (`\copy`), one server-side variant (`COPY ... FROM/TO`), a well-defined output-redirection family (`\o` / `\w`), and a large-object family (`\lo_*`). Same browser-vs-server filesystem split that dominates the MySQL file-I/O round: see [[OS Provider Seam]].

**Three priority decisions carried forward from Round 3 (Scripting) and MySQL Round 6:**

1. **"Save query result as..." download action ships ahead of `\copy`.** Cross-plane row — implemented once for MySQL and the same action lights up for Postgres. No change to ordering.
2. **`\copy` is less risky than MySQL's `LOAD DATA LOCAL INFILE`** (decided in Round 3). Postgres's `COPY FROM STDIN` / `COPY TO STDOUT` protocol is standardized and sqlx's Postgres support is mature; the spike risk that parked `LOAD DATA LOCAL` is absent here. `\copy` lands on the roadmap as real v0.0.2 work, not a deferred-spike item.
3. **`\o | command` (pipe output to shell) is BL** — browsers cannot spawn OS processes. Explicit row below; cites `OS Provider Seam.md`.

**One Postgres-specific surface** worth highlighting: the **Large Object (`\lo_*`) family**. Postgres's LO API is a separate storage model from `bytea` / `TEXT` columns — server-side blobs referenced by a numeric `oid`. Niche, but catalogued for completeness; nearly everyone uses `bytea` today.

### Admin

Server-level maintenance and control — the commands a DBA runs to *change server state or physical storage*, not introspect it. Same overall shape as MySQL Round 7: overwhelmingly T1 passthrough because Postgres admin is SQL-native. The cataloguing work is (a) counting every admin command so nobody re-proposes them, (b) extending the cross-plane **`\safe-mode` pattern list** with Postgres-specific destructive shapes, and (c) flagging surfaces where Postgres has no SQL equivalent (like `SHUTDOWN`).

**Decisions this round:**

1. **`\safe-mode` primitive is cross-plane.** The MySQL Round 7 design (`DbmsPlane::destructive_patterns() -> &'static [&'static str]`) already anticipated per-plane lists. Postgres's initial list differs from MySQL's in specifics but shares the plumbing.
2. **No SQL equivalent of `SHUTDOWN`** in Postgres — the server is stopped via `pg_ctl stop` externally or by SIGTERM to the postmaster. **Not a typed-SQL hazard**, so it's not on the safe-mode list. Flagged explicitly so readers understand why.
3. **`ALTER SYSTEM SET` is a persistent GUC change** (writes to `postgresql.auto.conf`) — interesting because it survives restarts. Flagged as **advisory + not-safe-moded-initially** (not immediately destructive), but a future safe-mode-list expansion candidate once the `UPDATE/DELETE-without-WHERE` round happens.
4. **`DROP OWNED BY` is Postgres-only and genuinely dangerous** — yanks every object owned by a role, cross-schema. Added to Postgres safe-mode list.

**Initial Postgres `destructive_patterns()` list (8 patterns):**

`DROP DATABASE`, `DROP SCHEMA`, `DROP TABLE`, `TRUNCATE`, `DROP ROLE`, `DROP USER`, `DROP TABLESPACE`, `DROP OWNED BY`. Mirrors the MySQL list's destructive shapes while dropping MySQL-specific items (`SHUTDOWN`, `RESET MASTER`, `RESET BINARY LOGS AND GTIDS`) that don't exist as SQL in Postgres.

### Auth

Role and privilege management — creating / dropping / altering roles (Postgres's unified users-and-groups model), granting and revoking privileges, inspecting grants, password management, **row-level security**, default privileges, and the `pg_hba.conf` auth-method surface. Everything in `pg_authid` / `pg_roles` / `pg_auth_members` / `pg_policy` / `pg_default_acl` and friends that's exposed through SQL. Excludes `pg_hba.conf` edits — those are on-server config-file changes, not SQL.

**Key structural difference from MySQL:** Postgres's **unified role model**. Roles are roles — a role WITH LOGIN is a "user", a role without is a "group". `CREATE USER` and `CREATE GROUP` are **aliases** for `CREATE ROLE WITH LOGIN` and `CREATE ROLE NOLOGIN` respectively (both historical). MySQL has distinct user + role entities with their own CREATE statements; Postgres folds both into `CREATE ROLE`. This shows up in the safe-mode list (`DROP USER` and `DROP ROLE` match the same underlying pattern in Postgres — they're aliases) and in how grants cascade.

**Key new feature material for Postgres:**

1. **Row-Level Security (RLS)** — `CREATE POLICY` / `ALTER POLICY` / `DROP POLICY` + `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`. MySQL has no direct analog. First-class Postgres feature; worth cataloguing in depth.
2. **Default privileges** — `ALTER DEFAULT PRIVILEGES IN SCHEMA ... GRANT ...` — privileges that apply to objects *created in the future*, not just existing ones. MySQL has no equivalent. Cross-plane `SHOW GRANTS` / `\dp` renderer needs to surface these separately.
3. **`SET SESSION AUTHORIZATION`** — temporarily become another user for the session. Different from `SET ROLE` (which activates a role you're already a member of). Superuser-only.

**Round-7 safe-mode list already covers the Postgres auth-destructive surface.** `DROP ROLE` / `DROP USER` (alias) / `DROP OWNED BY` (cleanup-before-drop-role) are already on the Postgres list. No expansions needed this round.

- ~32 rows catalogued. Auth is overwhelmingly T1 passthrough — Postgres's auth management is entirely SQL-driven, same story as MySQL Round 8.

### Shell Interaction

Combined round covering **Output Formatting**, **History & Editing**, **OS Escape**, and **Help & Discovery** — same structure as MySQL Round 9. Much of the material cross-refs cross-plane rows from MySQL; the genuinely-new Postgres content is the **`\pset` family** (psql's rich runtime format control — much richer than anything MySQL offers), the **local SQL help database** behind `\h KEYWORD`, and a handful of psql-only oddities (`\s filename`, `\setenv`, `\cd`).

**Key structural difference from MySQL:** psql has an order of magnitude more runtime formatting control than mysql does. `\pset format { aligned | unaligned | wrapped | html | asciidoc | latex | csv | ... }`, `\pset border { 0|1|2 }`, `\pset linestyle { ascii|old-ascii|unicode }`, `\pset null 'string'`, `\pset expanded auto` — these are all live toggles that change subsequent query output. MySQL has essentially only `\G`. **Our approach** from MySQL Round 9 — a `\output` runtime toggle with formats (table / vertical / csv / tsv / json / markdown / html) — already generalizes nicely. Most `\pset` commands map onto that single toggle plus a few per-format sub-options.

**Shell-level cross-plane features** (persistent history, Ctrl+R search, readline keybindings, tab completion) are catalogued against MySQL Round 9 and are shared across planes. They don't re-appear as T2-from-scratch rows here — just cross-refs.

## SQL dialect features (Axis 2)

Same framing as MySQL Axis 2 — the four places where SQL dialect coverage shows up on our side (from [[Dialect Coverage Framework]]):

1. **Syntax highlighting** — the Postgres-specific keyword + function list.
2. **Tab completion** — Postgres's keyword set plus schema metadata, via the shared cross-plane T3 tab-completion item.
3. **Multi-statement parsing** — includes **dollar-quoted strings** (the Round-3 parser T3 promotion).
4. **Dialect-specific UX hooks** — cross-plane hooks from MySQL Round 10 (**transaction-state indicator**, **schema-cache invalidation on DDL**) apply here with Postgres trigger patterns. Dollar-quoted-string tokenizer configuration counts as a parser UX hook, already catalogued.

Like MySQL Round 10, we don't enumerate every Postgres keyword or function. SQL-92 baseline is assumed. We call out **vendor-specific clauses, constructs, and quirks** that need attention. Most of what follows collapses into a **single keyword/function list audit pass** against the PostgreSQL 16 reference manual — one consolidated work item rather than ~50 individual tickets.

**Axis 2 summary — Postgres:**

- Most of Axis 2 reduces to a **single keyword/function list audit pass** against the PostgreSQL 16 reference manual. All the `T1 polish (audit)` rows collapse into one consolidated work item. Estimated scale: **~50 keyword/function additions** (slightly larger than MySQL's ~40 because Postgres's DDL and procedural surfaces are wider). One ticket: "audit + expand `POSTGRES_KEYWORDS` and `POSTGRES_FUNCTIONS` against PG 16 reference, including JSON / range / text-search / geometric / extension-authoring keywords + PL/pgSQL procedural keywords + dollar-quoted string highlighting."
- **One genuinely-new operator-highlighting polish item — T2.** Postgres is **much more operator-heavy** than MySQL: JSON (`->`, `->>`, `#>`, `@>`, `?`, …), range (`<<`, `>>`, `-|-`), geometric (`##`, `<->`, `?#`), regex (`~`, `~*`), text-search (`@@`). The Postgres highlighter currently renders operators as punctuation. **Add an operator table** to the plane's highlighter so operators render distinctly. Single infrastructure change; lights up ~40 operators. Flagged here because it's Postgres-specific weight, but the infrastructure (plane-driven operator table) is cross-plane.
- **Two UX hooks from MySQL Round 10 confirmed cross-plane** with Postgres-specific trigger patterns:
  1. **Transaction-state indicator** — Postgres adds a **"failed transaction" sub-state** (distinct colour) for the aborted-transaction case where every statement except ROLLBACK errors with "current transaction is aborted". MySQL has no direct equivalent (MySQL rolls back per-statement on error in most cases). One new indicator variant.
  2. **Schema-cache invalidation on DDL** — Postgres adds **rollback-aware cache invalidation**: DDL run inside a transaction can be undone by ROLLBACK, so invalidation has to trigger on both the DDL statement AND the subsequent commit/rollback. Same "best-effort, not comprehensive" contract as MySQL.
- **Dollar-quoted strings** in Postgres parser (T3) and highlighter (T1 polish) are a **single implementation effort** — tokenizer recognizes `$tag$`, parser respects it when splitting statements, highlighter renders the delimited content as string-literal style. One ticket, three surfaces.
- **Non-PL/pgSQL procedural languages explicitly out of scope** for highlighting. Writing PL/Python / PL/Perl / PL/V8 in our shell works (the content is still valid SQL after the function body), but inside `$$ ... $$` we don't apply a second language highlighter. That's a second-language-highlighter feature, not a parity feature.
- **Shell-layer SQL intercept track — final count for Postgres.** The Postgres interview adds to the cross-plane list: **advisory** patterns (Round 6 server-side COPY, Round 6 bare COPY FROM STDIN, Round 7 ALTER SYSTEM), **confirm-then-run** (Round 7 safe-mode, 8 patterns on Postgres), **post-query hook** (Round 2 warnings equivalent — Postgres auto-notices), **transaction-state indicator** (this round, with failed-tx sub-state), **schema-cache invalidation on DDL** (this round, with rollback awareness), **Activity-pane row-action hooks** (Round 5 terminate, pre-filled-shell handoff; Round 4 explain-this-query). The track total remains cross-plane — **6 shared shell-layer intercept items** across both planes plus plane-specific variants. One design doc, one infrastructure pass, lights up both dialects.

The Postgres inventory is now complete across both axes.

## Out of scope

Features we're intentionally not implementing. Different from BD in that these are either (a) covered by a better pattern already, (b) equivalent to something we already ship (psql's `\!` → in-shell commands), or (c) belong to a different product entirely (`pg_dump` / `pgAdmin`). Listed so a future contributor doesn't re-propose any of them.

| Feature | Why out of scope |
|---|---|
| `pg_hba.conf` / `pg_ident.conf` editing | Server-side configuration files, not SQL. DBAs edit them with a text editor and reload via `pg_reload_conf()` / `pg_ctl reload`. Listed so parity framing doesn't imply we manage this surface. |
| `createdb` / `dropdb` / `createuser` / `dropuser` / `initdb` / `vacuumdb` / `reindexdb` / `clusterdb` / `pg_resetwal` CLI binaries | Separate binaries that wrap SQL. Our shell supports the SQL forms; wrapping binaries aren't in scope for a browser SQL client. Cross-plane with MySQL's `mysqladmin` exclusion. |
| `pg_dump` / `pg_dumpall` / `pg_restore` / `pg_basebackup` | Separate binary products. Backup / restore is its own product surface — DBAs run these outside our shell. If we ever build a backup-management UI, that's a dedicated feature, not a parity row. |
| `pg_upgrade` / `pg_rewind` / `pg_waldump` / `pg_checksums` / `pg_controldata` | Offline-server tools. Not shell-interactive. |
| `pg_dumpall --roles-only` / `pg_dumpall --globals-only` | Role-definition export. CLI-binary path already excluded above; listed explicitly since DBAs know this flow. |
| PL/Python (`plpython3u`) / PL/Perl / PL/Tcl / PL/V8 highlighter support | Second-language-highlighter inside `$$ ... $$` bodies. Scope creep. PL/pgSQL is the default and the only one we highlight. Non-plpgsql function bodies render without special highlighting. |
