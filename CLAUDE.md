# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

**Parliament** — a browser-based SQL client built in Rust. Three-tier architecture:

```
Browser (Tyto / Leptos/WASM)  ←─WebSocket─→  Noctua (Rust backend)  ←─TCP─→  MySQL / PostgreSQL
```

Tyto (frontend) and Noctua (backend) are the two components. No desktop app. Frontend is pure browser WASM. Backend is a Rust binary that holds database connections and serves compiled WASM assets. Connections persist to `~/.sqlclient/connections.json`. See `ARCHITECTURE.md` at repo root for the full architectural overview.

## Commands

```bash
# Prerequisites (once)
rustup target add wasm32-unknown-unknown
cargo install trunk

# Development (two terminals)
cargo run -p noctua           # terminal 1 — backend on localhost:3000
trunk serve                   # terminal 2 — WASM dev server on localhost:8080, open this in browser

# Release build: one binary that serves the frontend itself (what
# .github/workflows/release.yml ships — push a `v*` tag for a draft release)
trunk build --release && cargo build --release -p noctua --features embed-frontend

# Check / lint
cargo check                           # native targets only (fast)
cargo check -p tyto --target wasm32-unknown-unknown  # check WASM frontend
cargo clippy
```

Backend must be restarted manually after backend code changes. Trunk hot-reloads the frontend automatically.

## Shell Behavior

- Prompt format: `N SQL>` where N is the query sequence number
- `;` at end of input + Enter → execute (horizontal table output)
- Input is read as the connection's CLI lexes it (`parser::Lexicon`, from `DbmsPlane::lexicon()`): psql's quotes, `E'…'` escape strings, `$tag$` bodies and nested `/* */`; mysql's backslash escapes, backticks, `#` / `-- ` comments, `/*!` as code, and outside quotes a backslash with the character it takes (`\'` opens no string, `\;` ends nothing). A backslash command typed after SQL — on the same line, or on a line of its own below — runs there, as both CLIs read a line: it starts at the line's first backslash outside quotes and comments (`parser::trailing_command`), the SQL before it being the query buffer, which the command works on or leaves where it was (`MetaAction::works_on_buffer`). psql's `\g`, `\gx`, `\gset`, `\gexec`, `\gdesc`, `\crosstabview`, `\watch`, `\e`, `\r` work on it (for the `\g` family the statements ended before it run first, as psql sends each at its `;`), mysql's `\e` / `\c` / `\r` too; any other command runs and leaves the buffer in the input, as both CLIs do — `select 1 as a \x` turns expanded output on and `select 1 as a` waits for its `;`; psql's `\echo`, `\set`, `\d`, `\c` …, mysql's `\s`, `\u db`, `\d //`, `\h` … the same; `\prompt` / `\password` take the input for the answer and give the buffer back after. A command takes what its CLI gives it (`DbmsPlane::command_extent`): psql's, its line; the mysql CLI's, `\` and its letter — or, with arguments (`\u`, `\d`, `\h`, `\?`), its line up to the delimiter after them, that included (`parser::mysql_command_len`; `\d` the one it sets) — and what's typed after it reads on as SQL, joining the buffer: `select 3 as c \s from dual;` shows status, then runs `select 3 as c  from dual` (the text around the command, joined as the CLI joins it); `select 4 \c select 5;` runs `select 5`; `\u mysql ; select 1;` changes database, then runs `select 1`. A `;` after a mysql command is the line's too: `\s;` and `\c;` end an empty statement — the CLI's `ERROR: ` / `No query specified` after the command — and `select 2 \s;` runs `select 2` after the status. A mysql command reads its arguments from the whole line, as the CLI hands them over: `\u sakila;` asks for database `sakila;` (`ERROR 1049 (42000): Unknown database 'sakila;'`), `\h select;` for topic `select;`, `\d //;` sets `//;`. A command typed first reads only its line. `nopager` (`\n`) and `notee` (`\t`) say what the CLI says — `PAGER set to stdout`, `Outfile disabled.`: a pane pages nothing and has no outfile — and `rehash` (`\#`) drops the shell's completion caches so the next Tab fetches the names afresh, saying nothing, as the CLI's (`MetaAction::RebuildCompletion`; pinned against the CLI under a pty by `tests/playwright/regression/mysql-nopager-notee-rehash.spec.ts`). `warnings` (`\W`) is the CLI's `com_warnings`: `Show warnings enabled.`, then after each statement with warnings, or one that fails, the server's `SHOW WARNINGS` before the next statement runs — `Warning (Code 1365): Division by 0`, a line each, but for a failure's own error alone (`shell::fetch_warnings`, a `warnings:` batch, `DbmsPlane::warning_lines`); `nowarning` (`\w`) `Show warnings disabled.` (pinned against the CLI under a pty by `tests/playwright/regression/mysql-warnings.spec.ts`). The mysql CLI's commands this shell doesn't run yet (`\R`, `\P`, `\T`, `\C`, `\.`, `\!`, `\x`) say `\T isn't supported here yet.` (`MetaAction::Fail`). The scrollback records the command alone, not the buffer; a buffer of `--` comments alone isn't kept, as psql doesn't add one (`parser::past_leading_line_comments`). The input is read in order, as both CLIs read theirs (`shell::process_input`): the statements ended before the first command (`parser::command_starts` → `shell::first_command`: a backslash command; on a line typed with nothing pending a named one — `use db`, `delimiter //`, `quit` (`DbmsPlane::named_command`); or, on MySQL, a statement its delimiter ends that is one — `status;`, `select 1; use db;` (`DbmsPlane::statement_command`)) run first, then the command, then what follows it, the same way — `select 1; \x` runs `select 1`, then `\x`; `insert …; \c other` inserts before switching; a pasted `DELIMITER //` … `DELIMITER ;` script runs as the mysql CLI runs it. Whatever the shell must wait for — those statements' results, a command's reply (`\d`, `\s`, `use`'s `USE`, a `\c` session), a prompt, a safe-mode confirm, a `\watch` — holds what's left in `ShellTab.resume_input` (`shell::shell_busy` says when it's free; an effect reads on then, outside the handler that freed it). Input entered meanwhile joins it — anything entered while the shell waits, with or without input left over — as type-ahead joins the CLI's, and text typed but not yet entered stays in the input; a lost session doesn't stop it (its next statement finds the session lost, or the reopened one, as the CLI's does); ON_ERROR_STOP drops it (`shell::drop_rest`), and a cancelled safe-mode confirm puts it back in the input. After `\e`, what follows comes back after the editor's text (`ExternalEdit.then`), as the mysql CLI appends it to the edited buffer — on psql that's the lines pasted below an `\e`, which now follow the edited text instead of being dropped. On MySQL `\g` and `\G` end a statement wherever they're typed, as `;` does (`select 1\G select 2;`). On psql a `;` stuck to a command's name is part of it, as psql's lexer reads a name: `\gx;`, `\x;`, `\echo;` are invalid commands, while the `\d` family reads its letters as psql's `exec_command_d` does — `\dt;` and `\dtq` list tables (`listTables` ignores letters it doesn't look for), `\d;` and `\df;` are unknown, `\dfa;` is `\df only takes [anptwSx+] as options` (pinned against psql 18 for every command).
- Statements keep their terminator as typed: the scrollback block, copy-block and history show `SELECT 1;` (or the `DELIMITER` string, `\G`, or the `\g` / `\gx` / `\gset` / `\gexec` / `\crosstabview` line), so recalling a statement and pressing Enter runs it again, as in psql / mysql. The server gets the statement without it (`TypedStatement { sql, terminator }`; `ShellEntry::Query.terminator`). A batch's last statement typed without one shows without one.
- Vertical-output terminator is dialect-native: MySQL connections end a statement with `\G` (mysql-CLI behavior). Postgres connections use `\gx` (one-shot, psql meta-command) or `\x` (sticky toggle). Each plane handles only its own native verb; cross-CLI shortcuts don't fire.
- Shift+Enter → newline within input
- Multi-statement paste: `SELECT 1; SELECT 2;` runs both sequentially and, as both CLIs do, keeps going past a statement that fails (psql's `ON_ERROR_STOP` is off by default; the mysql CLI has no such switch). With `\set ON_ERROR_STOP on` (PG) the rest is dropped silently, as in psql. Comments go where each CLI puts them. A statement of comments only goes to the server once it's ended (`parser::is_comment_only`): psql's at its `;` (`/* c */;`, `-- c` / `;`), Postgres answering with nothing; the mysql CLI (`--comments`, on by default) sends them too: a line comment starting a line with nothing pending is a statement of its own, ended by the line (`-- note` alone → the server's `Query OK, 0 rows affected`; a pasted script's header comments each get one); one after a statement on its line goes with that statement (`select 1; -- why`, shown in its block); an indented one, or one inside a statement, is part of the statement; a statement of block comments goes at its terminator (`parser::split_statements`, which also says whether the input ended a statement — `Statements.ended`). A statement ending in a line comment keeps the line break before its terminator (`select 1 -- why` / `;`), so it comes back from history runnable
- `DELIMITER //` (MySQL) changes the statement terminator for stored-proc authoring — the first word after it, set without a word, as mysql sets it; `delimiter ;` goes back; a bare `delimiter` is mysql's `ERROR: ` / `DELIMITER must be followed by a 'delimiter' character or string`
- A terminator that ends nothing — `;` alone, the second `;` of `select 1;;`, mysql's `\g` / `\G` alone or `\G;`, a `DELIMITER` string alone — is answered as each CLI answers it (`DbmsPlane::empty_statement`, `shell::cli_answer`): the mysql CLI's `ERROR: ` / `No query specified`, in order with the input's other statements (`parser::split_statements` keeps the empty statement; `shell::next_statement` says it when the queue reaches it — no session needed); psql sends it, as it sends what its buffer holds, even nothing. So does psql's `\g` family with no query at all — empty buffer, no previous query — and a `/* */` comment before `\g` is a buffer it sends (`--` comments alone aren't one). The server answers an empty query with nothing: psql prints no more than its `Time:` under `\timing`; `:ROW_COUNT` is 0; under `AUTOCOMMIT off` the `BEGIN` before it opens a transaction; and it's the previous query (`\p` after `;` prints `;`). `\gdesc` with no query describes the empty one — `The command has no result, or the result has no columns.` — and `\watch` refuses it, `\watch cannot be used with an empty query` — but after a `;` watches that, as psql's watches its previous buffer, each run printing only its `Time:` under `\timing`. Pinned against psql by `tests/playwright/regression/empty-statements.spec.ts`
- Dollar-quoted strings (Postgres) are recognized: `$$ ... $$` won't split on internal semicolons
- Arrow Up/Down → walk command history with prefix matching (type `SELECT` + up-arrow filters to SELECT commands)
- Meta-commands are recorded as typed, like psql: `\d film`, `\x`, `\dt` … show as a block in the scrollback and come back on Up-arrow / Ctrl+R (persisted) — the command, never the catalog SQL it expands to. The `\g` family records its buffer with the `\g` line; `\e` and a buffer-clearing `\c` aren't recorded; `\password` never is. Meta entries (`ShellEntry::Query.meta`) don't count as "the previous query" for `\g` / `\watch` / `\e`, nor does a query a `\watch` ran — psql's previous query is the last buffer its `;` or a `\g`-family command sent (`shell::last_query`).
- Ctrl+R → reverse incremental search across persistent history
- Readline keybindings: Ctrl+A/E (start/end), Ctrl+U/K (delete to start/end), Ctrl+W (delete word back)
- History persists to localStorage keyed by connection identity; survives page refresh and crashes. It keeps what was typed — `:var`s unexpanded, and an empty-buffer `\g` as just `\g` — and never anything that may hold a secret (`history::may_hold_secret`): any `\set` / `\setenv`, anything mentioning password / passwd / pwd / identified / secret / credential / crypt / hmac, and any URI with a user part (`postgresql://bob:pw@host/db`). Such lines still show in the scrollback and walk with Up-arrow for the session, but aren't saved; entries saved before the rule are removed the next time the history is read. noctua's log never carries statement text either: sqlx's statement log (`sqlx::query`) and notice log are forced off whatever `RUST_LOG` says (`notices::log_filter`); notices still reach the shell
- Clicking anywhere in shell area focuses the input
- Auto-focuses on session connect
- `\x [on|off|auto]` (and `\pset expanded` / `\pset x`) is psql's expanded display (`types::Expanded`): a value sets it — `auto` in any case, or a Boolean as psql reads one — no value toggles on ↔ off (`auto` goes off), anything else is psql's `unrecognized value "x" for "expanded"` / `Available values are: on, off, auto.`; each says psql's `Expanded display is on.` / `… is off.` / `… is used automatically.`. On, every result shows vertically — every statement of a multi-statement input too, and every list (`\dt`, `\l` …), as psql's `printQuery` prints them. Under `auto` a result shows vertically only when psql's aligned table would be wider than the pane and has more than one column (aligned and wrapped only, as psql's printTable decides), the pane's width in characters playing psql's terminal width (`DbmsPlane::expands_automatically`, `print::aligned_width`, `dom::shell_columns`; a pane that can't be measured never expands, as psql off a terminal)
- `\timing [on|off]` (PG) is psql's: off until turned on (the mysql CLI always times, so MySQL shells do — `DbmsPlane::timed_by_default`); an unknown value says psql's `unrecognized value "x" for "\timing": Boolean expected`. Times print as each CLI prints them (`DbmsPlane::timing`): psql's `Time: 0.205 ms` on a line of its own under the result or tag — past a second `Time: 1205.003 ms (00:01.205)` (`postgres.rs::psql_time`, a port of `PrintTiming`) — mysql's `(0.002 sec)` at the end of the footer. noctua measures microseconds (`exec_time_us`). Each result keeps whether it was timed when it arrived (`timed` on `ShellEntry::Table` / `Vertical` / `Info`): a later `\timing` doesn't rewrite earlier output, as in psql. A list (`\dt`, `\dn` …) is never timed, as psql's `PSQLexec` runs it untimed
- `\safe-mode on` gates destructive commands with an inline confirmation. AST-based (via `sqlparser-rs`) — sees through leading comments and whitespace. Flagged shapes: DROP, TRUNCATE, `DELETE` / `UPDATE` without WHERE, `ALTER TABLE … DROP COLUMN / CONSTRAINT / FK / INDEX / PARTITION`, DROP ROLE. Statements run by the `\g` family are gated like any other. Multi-statement pastes show one up-front dialog listing every destructive statement in the batch — the DBA signs off (or doesn't) on the whole batch atomically. Tautological WHERE clauses (`WHERE 1=1`) are trusted as the DBA's intentional ritual. If sqlparser-rs can't parse a statement, safe-mode treats it as destructive with a "couldn't parse — confirm if safe" message rather than refusing to send.
- Transaction indicator badge in toolbar (yellow TXN / red TXN FAILED), and psql's `%x` in `PROMPT1` (`*` / `!`), follow the server, never the SQL typed: after every command on a session noctua sends the transaction status the server reported (`ServerMessage::TransactionStatus`, just before the reply) — Postgres's ReadyForQuery (libpq's `PQtransactionStatus`), MySQL's `SERVER_STATUS_IN_TRANS` (after an error, whose reply carries none, from the ping noctua sends) — both exposed by the patched sqlx drivers (`vendor/`). So on Postgres `ROLLBACK TO SAVEPOINT` clears TXN FAILED and a failing `\d` inside a transaction fails it, as psql shows; on MySQL a write under `autocommit = 0` lights the badge and DDL's implicit commit — even DDL that then fails — clears it. MySQL has no failed state (an error doesn't end its transaction, or ends it outright). A session that's gone (killed, noctua restarted) has no transaction: the badge clears. Pinned live by `cargo test -p noctua -- --ignored pg_transaction_state_follows_the_server mysql_results_and_transactions_match_the_cli`.
- `\watch [[i=]SEC] [c=N] [m=MIN]` is psql's: it runs the query buffer before it (`select now() \watch 1`) — or, when that's empty, the last query — every SEC seconds (a fraction allowed, `0` too; 2 by default), and prints every run as psql does, one after another (`shell::print_watch_run`): a title — the time the run started, in C's `%c` shape and the browser's time zone, and the interval, `Mon Oct 12 07:40:40 2026 (every 0.5s)`, after `\pset title` and a tab when one is set (`watch_title`) — that is the result's own title, as psql hands it to its printer: ending its line itself, a blank line after it, centred over a grid like any title, first in expanded output (`shell::result_entry`: `\x`, `\pset format`, footer, `Time:` with `\timing`); a command prints just its tag each run. Its notices print with each run. An error prints and ends the watch; `count` ends it after N runs and `min_rows` after a result with fewer rows (that run still printed), without a word, as psql's does. While it runs a bar under the output says how often, with Stop. What's entered meanwhile waits, as psql reads type-ahead only once its watch is over (`resume_input`): it runs after a watch that ends itself — its count, `min_rows`, an error. Ctrl+C in the input stops the watch, as in psql, and so does Stop, its button — and what was typed or pasted after it goes with it, as the terminal flushes its input at psql's SIGINT (`interrupt_watch`). A watch whose session is lost is over, as psql's ends when its next run finds the connection gone: that run resets it as any command does (libpq's lines, `Attempting reset: Succeeded.` — `shell::resets_lost`), and what was typed meanwhile runs on the new one. Arguments are read as psql reads them (`parse_watch_args`, a port of `exec_command_watch`: `i=` / `interval=`, `c=` / `count=`, `m=` / `min_rows=`, an unlabelled one the interval) and refused in its words (`\watch: incorrect interval value "x"`, `incorrect iteration count "0"`, `interval value is specified more than once` …). It leaves the result variables as they were — a run's rows and a failed run's error alike, as psql's (`is_watch`); `\errverbose` still shows the error. It leaves the previous query as it was, as psql's runs its buffer itself: `\p`, and an empty buffer's `\g`, `\gdesc`, `\e` and `\watch`, use the query sent before it (pinned by `tests/playwright/regression/psql-watch.spec.ts`).
- `\prompt [text] name` interactive variable read. The optional text supports single- or double-quoted strings (for spaces). Enter assigns the current input to the named variable, silently as psql's; Esc cancels. Routes through the same `psql_vars::classify` rules as `\set` — read-only names refused, honored names get behavioral effects (e.g. `\prompt 'ON_ERROR_STOP off|on' ON_ERROR_STOP` flips the multi-statement abort policy).
- Save result as CSV / JSON / SQL download links on every result
- `\set name [value …]` + `:name` / `:'name'` / `:"name"` / `:{?name}` client-side variables, expanded where psql expands them (Postgres only — `DbmsPlane::interpolates_variables`; the mysql CLI has no `:var`s, so a MySQL statement goes as typed). In a statement (`ShellTab::interpolate` → `parser::substitute_vars`): only in code — not in quoted strings, comments, dollar-quoted bodies or the `::` of a cast (`parser::Lexicon::Psql`). In a backslash command's arguments (`pattern::slash_args`, psql's `OT_NORMAL` lexer): outside quotes, the value becoming part of the argument it's in, spaces and all — never re-split; the arguments of `\h`, `\sf`, `\sv`, `\ef`, `\ev` are read whole and unexpanded, as psql reads them. `:name` is the value, `:'name'` the value as libpq's `PQescapeLiteral` writes it (quotes doubled; with a backslash, ` E'…'`), `:"name"` as `PQescapeIdentifier` writes it, `:{?name}` `TRUE` / `FALSE` for whether it's set; an unset one stays as typed (`parser::variable_reference`). Every command reads its arguments that way (`slash_args` before the plane's dispatch; `MetaContext.variables`), so `\echo` prints them a space apart (`\echo 'a  b'` → `a  b`), `\set` joins its values (`\set z a b c` → `abc`), `\C` / `\pset title` take one argument (quote a title with spaces), and an unterminated quote is psql's `unterminated quoted string` (for a command the plane handles). A trailing `;` stays on the last argument where psql keeps it — `\echo`, `\set`, `\unset`, `\pset`, `\gset`, `\timing`, `\crosstabview` (`KEEPS_SEMICOLONS`: `\echo a;` prints `a;`, `\timing on;` is psql's error) — and goes elsewhere, outside quotes only (`\d film;`, `\x on;`). SQL a command generates isn't expanded. `\set` / `\unset` say nothing when they work, as psql's; psql's errors otherwise (`invalid variable name: "a-b"`, `\unset: missing required argument`, `unrecognized value "x" for "ON_ERROR_STOP": Boolean expected`). **psql predefined variables** are recognised via `psql_vars::classify`:
  - **Read-only (auto-populated)**: `:USER`, `:DBNAME`, `:HOST`, `:PORT`, `:ENCODING` (`UTF8`), `:VERSION`, `:VERSION_NAME`, `:SERVER_VERSION_NAME`, `:ERROR`, `:LAST_ERROR_MESSAGE` (the primary message), `:LAST_ERROR_SQLSTATE` (`00000` until an error), `:SQLSTATE` (the last command's: `00000` on success), `:ROW_COUNT` (`0` after an error). Populated at `SessionOpened` / `QueryError` / `QueryResult`, as psql's `SetResultVariables` does (`shell::set_result_variables`; a `\gexec`'s once the statements it generated have run) — for the user's commands only, not a meta-command's own catalog queries or a `\watch` run (whose errors `\errverbose` still shows). `\set` of these is refused.
  - **Honored**: `ON_ERROR_STOP` (default `off`, as in psql: multi-statement input continues past errors; `on` → the rest is dropped, silently as psql does). `AUTOCOMMIT` and `ON_ERROR_ROLLBACK`, as psql's `SendQuery` honours them around every statement it sends — typed, batched, the `\g` family, `\gexec`'s, `\gdesc` (not `\watch` runs or a meta-command's own SQL): with `AUTOCOMMIT off`, outside a transaction, `BEGIN` first unless the statement ends / begins one or can't run in one (`postgres.rs::command_no_begin`, a port); with `ON_ERROR_ROLLBACK on` — or `interactive`, as this shell is — in a transaction, `SAVEPOINT pg_psql_temporary_savepoint` first, and once the statement has answered `ROLLBACK TO` it in a failed transaction or `RELEASE` it in an open one, unless the statement's tag says it ended or replaced it (`COMMIT` / `ROLLBACK` / `RELEASE` / `SAVEPOINT`, psql's `svpt_gone`). The plane says what goes around (`DbmsPlane::statement_opening` / `statement_closing`); the shell sends it on the session as batches of its own (tag `txn:<n>`, `shell::send_user_statement` → `continue_wrap` → `close_wrap`, state in `ShellTab.wrap`, part of `shell_busy`), so their replies are never taken for the statement's, and goes on once the last has answered; a refused `BEGIN` / savepoint prints its error and the statement doesn't run; a session found dead there resets as psql's does. One difference: psql runs `\gexec`'s statements inside the generating query's savepoint, here they run after it's closed — the same end state unless a generated statement sets or releases savepoints itself. Variables with psql's hooks are set as psql sets them (`psql_vars::assign` → `shell::set_variable`, for `\set`, `\unset`, `\prompt`): a bare `\set` of a Boolean is `on`, `\unset` stores `off` (`VERBOSITY` `default`, `SHOW_CONTEXT` `errors`), values kept as typed (`of`), refusals in psql's words (`unrecognized value "x" for "ON_ERROR_ROLLBACK"` / `Available values are: on, off, interactive.`); each starts at psql's value (`psql_vars::DEFAULTS`: `:AUTOCOMMIT` is `on`). The Schema tab also has a dedicated **TOAST** section sitting between Indexes and Relationships, with three layouts driven by the `toast:*` introspect: (a) `Single` — normal table with TOAST, showing its `pg_toast.pg_toast_NNNNN` table name (clickable → detail view), Heap size, Index size, Rows (est.), Storage ratio, plus a "Toastable columns" sub-table listing the non-PLAIN attstorage columns (`EXTENDED` / `EXTERNAL` / `MAIN` — PLAIN filtered out server-side); (b) `PartitionAggregate` on a partitioned parent — Partitions count, Total TOAST across leaves, and a clickable Largest TOAST leaf; (c) `IsToastOf` when the DBA opens a `pg_toast.*` relation — replaced by a `TOAST OF <parent>` back-link at the top of the Schema tab (parent name clickable, navigates back). Suppression semantics match the Overview cell: hidden when no TOAST relation exists, when TOAST is empty, on partitioned parents whose leaves collectively have no TOAST, and on MySQL. TOAST relation navigation works because `ensure_table_detail_loaded` accepts arbitrary schema names — no SQL filter blocks `pg_toast` lookups. A **Dead tuples %** cell (severity ≤5% green / 5-20% yellow / >20% red — mirrors PG's `autovacuum_vacuum_scale_factor` default of 0.2) sits next to Last vacuum as its forward-looking companion, answering "is vacuum keeping up?"; higher values mean autovacuum is falling behind or being blocked by a long-running transaction holding back the xmin horizon. A **Freeze age** cell (integer percentage of `age(relfrozenxid) / autovacuum_freeze_max_age`, severity <50% green / 50-100% yellow / >100% red) answers "how close is the table to triggering an anti-wraparound vacuum?" — pure relation-level catalog math via `pg_class.relfrozenxid` + the `autovacuum_freeze_max_age` GUC, no page scans or visibility-map probing so it's safe on TB-sized tables; values above 100% mean autovacuum should already be running and something is blocking it (typically a long-running txn holding the xmin horizon). PG-only; rolls up as MAX across leaves on partitioned parents (worst leaf drives urgency, not average); a per-table `autovacuum_freeze_max_age` only counts when smaller than the cluster value (`LEAST`). Classifier + tooltip live in `crate::storage_factor::classify_freeze_pct` / `build_freeze_tooltip`. MultiXact age is a row in the Storage tab's Autovacuum trigger table. Suppressed when `age()` returns 0 (temp / unlogged / brand-new). After the header cleanup, the header meta-grid renders in the order Engine / Owner / Rows / Data / Index / TOAST / Cache hit / Block IO / Index access / CRUD / Last vacuum / Last analyze / Freeze age, still matching a DBA's mental walk-down (identity → volume → runtime signals → maintenance). The deeper "storage geometry" cells (Storage factor / Pages·Ideal / Avg row / Dead tuples %) moved to the **Storage tab**; stale statistics and MultiXact age are now Analyze / MultiXact rows in its Autovacuum trigger table, measured against the table's effective settings. See the Storage Tab section below. Severity comes from `crate::storage_factor::classify`; tooltip text from `build_tooltip` with `TooltipTarget::Table` (suggests VACUUM FULL / OPTIMIZE TABLE). The **Pages / Ideal** cell renders the same actual-vs-ideal pair as a raw page count (e.g. `~64 / ~51`); label collapses to "Pages" when the ideal estimate isn't available. On partitioned parents (PG `c.relkind = 'p'`), Pages / Ideal / Storage_factor / Storage_actual_bytes all roll up as sums across leaf partitions via `pg_partition_tree` — the parent's own `relpages` is 0 since it owns no data, so a rollup gives the DBA a real number instead of a wall of zeros. Storage_factor on a parent reads as `sum(actual pages) / sum(ideal pages)` — the whole partitioned table's average efficiency. The Indexes tab gets a per-index **Storage** column on PG (btree only — non-btree types and MySQL skip the column entirely). Same multiplier framing as the table factor; per-index ideal pages = `leaf_pages + 1 meta + (1 internal-root when leaf>1)` where `leaf_pages = CEIL(reltuples × (key_width + 18) / 8152)`. The +1/+2 overhead matters for small indexes — without it a 3-leaf integer PK reads as 1.7× false bloat (actual 5 = 3 leaves + 1 internal + 1 meta vs leaf-only ideal 3). Factor clamped to a 1.0× floor; tooltip uses `TooltipTarget::Index` (suggests REINDEX). The Indexes **Size** column on PG also paginates to **Size / Ideal** when at least one index has an ideal-bytes estimate (e.g. `312 KB / 352 KB`); MySQL keeps the plain `Size` header since no per-index ideal is computable. The Indexes tab also gets a **Uses** column on PG sourced from `pg_stat_user_indexes` — scan counts since the last stat reset, paired with the average entries returned per scan (`idx_tup_read / idx_scan`) as a diagnostic suffix: `"1,234 (2.3 avg)"`. Zero counts colour red (`.metric-bad`, drop candidate); non-zero scans show plain text with the avg in parentheses. The avg-per-scan is informational only (no severity on it — high values can mean range scans or low selectivity, but neither is wrong by itself). MySQL doesn't emit the column (no equivalent in core InnoDB stats). Caveats: when MySQL has `innodb_file_per_table=OFF` the factor reflects the shared tablespace and is misleading; PG estimate degrades when the table has never been analyzed (returns empty / hidden).

Errors excerpt the SQL actually sent (`ShellTab.sent_sql`, recorded by `shell::send_statement` — every query a shell sends goes through it except `\password`'s, whose hash must not reappear): the failing statement of a batch, not the last one, is marked; a statement `\gexec` generated is excerpted as sent, with no entry to mark (`shell::failed_command`). Meta-commands' own errors follow psql too: `\d <pattern>`'s catalog batches carry the fields (`BatchResult.error: Option<DbError>`) and print by `VERBOSITY`, kept for `\errverbose` but not in the result variables; `\ef` / `\ev` lookups (`IntrospectError.error`) print psql's `minimal_error_message` — `ERROR:  <message>` whatever `VERBOSITY` says (`Verbosity::Minimal`) — and psql's own refusal prints bare (`"s.m" is not a view`). `\errverbose` re-prints the last error (`ShellTab.last_error`) with every field (`VERBOSITY verbose`, `SHOW_CONTEXT always`), or psql's `There is no previous error.`
- ~50 `\d*` metadata commands covering schemas / roles / relations / functions / aggregates / procedures / types / extensions / FDWs / partitions / text-search / event-triggers / replication / extended-statistics / access-methods / tablespaces / server-config / per-role-and-db settings
- `\d <pattern>` prints exactly what psql 18 prints (`tyto/src/plane/postgres/describe.rs`, a port of describe.c's `describeTableDetails` / `describeOneTableDetails` for PG 13+): every relation kind — table, partitioned table and partition, view, materialized view, index and partitioned index, sequence, TOAST table, composite type, foreign table — with psql's title, columns and footers (indexes, constraints, referenced-by, policies, statistics objects, rules, publications, triggers, partitions, inheritance, tablespace …), laid out by psql's aligned printer (`print.rs`). `+` adds psql's verbose columns and footers, a pattern matching several relations prints each, `\t` prints rows only, `\pset format` applies, and — as in psql — `\x` doesn't, but for a sequence. It runs psql's own catalog queries as **staged batches**: `MetaAction::Staged` sends the first `IntrospectBatch` (the server version + psql's lookup), each reply goes back to the plane (`DbmsPlane::meta_continue`, which re-reads the command; nothing is kept between steps) for the next batch — each relation's `pg_class` row, then every section it needs, then, only for an index in a non-default tablespace, the tablespace's name — and the result lands as `ShellEntry::Printed` (`ShellTab.pending_meta`, nonce-tagged `meta:<n>`, cleared on reconnect). The printed title of a table / partitioned table / TOAST table / view, and the `for table "s.t"` in an index's footer, link to the Schema Explorer (opens next to the shell on the shell's database, inspector expanded); the block's right-click menu offers the same as "Open s.n in Schema Explorer". `\d` without a pattern lists relations (psql's `listTables`). Byte-for-byte parity is pinned live: `cargo test -p tyto -- --ignored describe_matches_psql` (Pagila, plus a fixture built in a never-committed transaction that covers every footer).
- **`use db`** (MySQL) is the mysql CLI's `use`: typed (`use db`, `\u db`) or a `USE` statement of a batch, it prints `Database changed` instead of the server's "Query OK" — onto another database after `Reading table information for completion of table and column names` / `You can turn off this feature to get a quicker startup with -A`, as `com_use` rebuilds its completion (`DbmsPlane::completion_notice`; the CLI asks the server for its database first, this shell compares the one it tracked: so a name differing from the server's only in case, on a server that folds names, or a change it didn't see — the database it's on dropped from under it — can say it where the CLI doesn't, or not where the CLI does) — and the shell is then on that database — tab label, `:DBNAME`, where a reconnect goes (`DbmsPlane::switches_database`, read off the SQL sent). `use db; select …` ends `use` at its `;`, the rest runs after. A bare `use` prints mysql's `ERROR: ` / `USE must be followed by a database name`. Pinned by `tests/playwright/regression/mysql-use.spec.ts`.
- **`help topic`** (MySQL; `\h topic`, `? topic`) is the mysql CLI's `com_server_help`: the server's `HELP 'topic'` (`plane/mysql.rs::server_help_query` — the topic as typed after the command's first space, quoted as the CLI quotes it, cut to its 101 bytes), staged (`MetaAction::Staged` → `DbmsPlane::meta_continue`), its answer printed as the CLI prints each shape — one topic (`Name:` / `Description:` / `Examples:`), several items or a category's contents (lists under `categories:` / `topics:`), `Nothing found` — or the server's error (`server_help_lines`). Without a topic, the CLI's command list. Pinned against the CLI under a pty by `tests/playwright/regression/mysql-server-help.spec.ts`.
- **`connect [db [host]]`** (MySQL, `\r`) is the mysql CLI's `com_connect`: its arguments read as `get_arg` reads them (a word, or one quoted with `'`, `"` or `` ` ``, a backslash keeping the next character; from the whole line, as the CLI hands it over — `\r sakila;` asks for `sakila;`), the buffer cleared, the session closed and a new one opened (`MetaAction::Connect` → `shell::connect_anew`, `Reopening::Connect`) on the database named or the one it's on, which is the shell's database from then on. It says `Connection id:    N` / `Current database: db` (and a blank line), after `Reading table information for completion of table and column names` / `You can turn off this feature to get a quicker startup with -A` when a database was named (`DbmsPlane::completion_notice`). A database the server refuses prints its error (`ERROR 1049 (42000): Unknown database 'x'`, `connect_failed`) and leaves no connection: the next statement's reconnect tries that database again and says `Can't connect to the server`, as the CLI's does. A host other than the connection's isn't supported yet (it needs credentials of its own). Pinned against the CLI under a pty by `tests/playwright/regression/mysql-connect.spec.ts`.
- **Named commands** (MySQL) are read as the mysql CLI's `find_command` reads them (`plane/mysql.rs`: `NAMED_COMMANDS`, its 27 names, each run as its letter is — `status` as `\s`, `help select` as `\h select`): the name in any case, past leading whitespace and `/* */` comments, arguments only for a command that takes them (`status foo;` goes to the server). A line typed with nothing pending is one (`DbmsPlane::named_command`) unless it has `\g` or the delimiter in it (`delimiter //;` aside); then — as everywhere — each statement its delimiter ends is one when its text is (`DbmsPlane::statement_command`, mysql's `add_line`): `status;`, `help select;`, `select 1; Status ; select 3;` run in order, the statement recorded as typed (`status;`). `go` / `ego` alone answer the empty buffer (`No query specified`); as a statement they send their own name, which the server refuses, as the CLI's do. The ones this shell doesn't run yet say so by name (`tee isn't supported here yet.`); `use` with a backtick sends the text typed, as the CLI's `normalize_dbname` does. A named command typed alone takes its whole line, as the CLI hands it over: `use db \s` is `use db` (the `\s` never runs). psql has no such statements: `select 1; quit;` goes to the server. Pinned by `tests/playwright/regression/mysql-named-commands.spec.ts`.
- **psql's assistance words** (`help`, `quit`, `exit`) are read as psql 18's `MainLoop` reads them (`plane/postgres.rs`: `assistance_word`): at the very start of a line, in any case, with only whitespace after them and maybe one `;` (`QUIT;`, `help ;` — not `  help`, `helpme`, `quit;;`). With nothing pending (`DbmsPlane::named_command`) `help` prints psql's pointers (`You are using psql, the command-line interface to PostgreSQL.` / `Type:  \copyright for distribution terms` …) and `quit` / `exit` close the shell, as `\q` does — in an inactive `\if` branch too, as psql reads them before its branches. With a statement pending they stay in it, as text, and psql's note shows as psql reads the line (`DbmsPlane::line_notes` — when the statement holding it is sent, or at once while it waits, as for the mysql CLI's notes): `Use \? for help or press control-C to clear the input buffer.`, `Use \q to quit.`, inside a quote or comment `Use control-D to quit.` — as for a `\q` typed there. The pending buffer is psql's, replayed from the lines before (`psql_query_buffer`): a `/* */` comment counts, a `--` one doesn't, a command that works on the buffer (`\g`, `\r`) empties it. psql has no `status`: it goes to the server. Pinned by `tests/playwright/regression/psql-assistance-words.spec.ts`.
- **`\c [-reuse-previous=on|off] [dbname [user [host [port]]]]`** (PG) is psql's: arguments read as psql reads them (`-` or nothing keeps the current value, double quotes keep case; `-reuse-previous=`, first only, takes a Boolean as psql reads one — `on` is as without it, a bad value is psql's `unrecognized value "x" for "-reuse-previous": Boolean expected` and nothing connects, `off` (libpq's defaults for the rest) isn't supported yet; `postgres.rs::psql_connect`); the new session opens while the previous one stays (`ShellTab.switching`), which closes only once the new one is open. Success prints `You are now connected to database "d" as user "u".` — with `on host "h" at port "p"` when there was no connection before (`DbmsPlane::connected_notice`); failure prints libpq's `connection to server at "h", port p failed: FATAL:  database "x" does not exist` (the server's fields ride on `SessionError.error`) and `Previous connection kept` (`connect_failed`), the session unchanged. A bare `\c` reconnects to the same database; after a failed reset it says `No database connection exists to re-use parameters from`. Another user, host or port, or a connection string, isn't supported yet and says so. The new session has no transaction. Pinned by `tests/playwright/regression/psql-connect.spec.ts`.
- Panes reconnect to the database they were on — after noctua restarts, from the "Session ended → Reconnect" banner, and when a closed tab is reopened — not the connection's default (`ShellTab::reconnect_database`).
- **A lost session carries on as the native CLI does** (`DbmsPlane::lost_connection` → `LostConnection`; no "Session ended" banner on a shell — other panes keep it):
  - **MySQL** — on its next statement, as the mysql CLI does (`--reconnect`, on by default): the statement's block shows `ERROR 2013 (HY000): Lost connection to MySQL server during query` / `No connection. Trying to reconnect...`, then — once noctua opens a new session on the same database — `Connection id:    N` / `Current database: db`, then its result. A statement that finds the connection dead (`QueryError.connection_lost` with no server error — never after a server error such as a KILL's 1317) runs again in the new session, the rest of its batch after it, twice at most (`reopen_retries`), as mysql's client does. A reconnect that fails shows the server's error as the CLI prints it (`ERROR 1049 (42000): …`), then its `ERROR: ` / `Can't connect to the server`, the statement unrun — a connection it couldn't make at all in noctua's words (mysql's `ERROR 2003 …` isn't ported yet); after one, the next statement skips the 2013 line, as the CLI does. `Current database:` ends with a blank line, as `com_connect` prints it.
  - **Postgres** — at once, as psql's `CheckConnection` does: the command that found it lost (a statement, or a `\d`'s catalog batch — `IntrospectBatchResult.connection_lost`) prints the server's `FATAL:` (if it sent one) and libpq's `server closed the connection unexpectedly` lines, the connection is reset, `The connection to the server was lost. Attempting reset: Succeeded.`, and the rest of the input runs on the new one (unless `ON_ERROR_STOP`); the command itself isn't run again. A loss noticed by background work (completion, the explorer) resets nothing — psql learns of it from a command, so the next statement does: libpq's lines and the reset, without running it (`SendTo::Reset`). A failed reset prints `…Attempting reset: Failed.` twice (psql 18 tries twice) and every statement until `\c` prints `You are currently not connected to a database.`; `%R` / `%x` in `PROMPT1` read `!` / `?` (psql's `!?>`) and the connection's own codes print nothing (`ShellTab.disconnected`).
  - Mechanics: user statements go out through `shell::send_to` → `SendTo::{Session, Reopen, Reset, NotConnected}` → `shell::deliver`; a replacement session in flight is `ShellTab.reopening` (`Reopening::Resend(sql)` for mysql, `Reset` for psql), settled by SessionOpened / SessionError. The transaction is gone either way, as in the CLIs. Pinned by `tests/playwright/regression/{mysql-reconnect,psql-reset}.spec.ts`; the failed paths were checked by hand through a TCP proxy killed mid-session.
- **`\d*` modifier suffixes**: every `\d*` command reads its options as psql 18 does — `S` (system objects) and `+` (verbose) anywhere after the command's letters, in either order — and they act where psql's do: both on `\d`, `\dt` `\dv` `\di` `\ds` `\dm` `\dE`, `\dn`, `\df*`, `\du` / `\dg`, `\dT`, `\dD`, `\do`, `\dc`, `\dL`, `\dO`; only `S` on `\da`, `\dp`, `\drg`, `\dd`; only `+` on `\l`, `\dx`, `\db`, `\dP`, `\dconfig`, `\dC`, `\dy`, `\dF*`, `\dA*`, `\de*`, `\dR*`, `\dl`; neither on `\dX`, `\ddp`, `\drds` (accepted and ignored elsewhere, as psql does). psql 18's `x` (show this result expanded: `\dtx`, `\dfx`, `\lx` — `\dx` stays extensions) works on all of them except the per-object printed ones (`\dx+`, `\dF+`, `\dFp+`, `\dRp+`), and never straight after `\d`, where it spells `\dx`. A suffix psql doesn't take for a command (`\dFS`, `\dAS`) makes it unknown, as in psql.
- **psql name patterns** (`tyto/src/plane/postgres/pattern.rs`, a port of psql's `patternToSQLRegex` / `processSQLNamePattern` / `validateSQLNamePattern`, emitting psql's SQL text): `*` / `?`, `schema.name` (and `db.schema.name`, refused with psql's "cross-database references are not implemented" unless it names the shell's database — `MetaContext.database`, passed through `DbmsPlane::meta_cmd_in`), double quotes keep case and make characters literal, unquoted ASCII letters fold to lower case, other regex characters pass through outside quotes (`\dt (film|actor)`), `$` and `[]` are always literal. Arguments split the way psql reads them (`pattern::slash_args`: double quotes kept, single quotes stripped; an unterminated quote is psql's `unterminated quoted string`). `\d` without a pattern and `\dt` `\di` `\dv` `\dm` `\ds` `\dE` — alone or combined, `\dtv` — are psql's `listTables`: same SQL, columns (`Schema | Name | Type | Owner`, `\di` adds `Table`, `+` adds `Persistence | Access method | Size | Description`), title (`List of relations`, or `List of tables` … for one kind) and messages (`Did not find any tables named "x".`); without `S` or a pattern, system schemas are left out. `\dn` (listSchemas — with a pattern, on PG 15+, psql's second query for the publications of the schema the pattern names, put in as typed as psql puts it, whose names print under the rows as its `Publications:` footer in place of the row count: `MetaAction::List.footers` → `FooterQuery`, the list's result held in `ListReply.held` while it runs, `PrintedWith.footers` — psql's `myopt.footers` — in the grid, expanded, every `\pset format` and "Copy output", under `\pset footer off` too, never under `\t`; ## Storage Tab (per-table)

Sits between Schema and DDL in the tab strip. Answers the "physical shape" questions that would otherwise clutter the at-a-glance header. Three sections, top to bottom, each reactive on its own signal and each a compact `.schema-table`-style table (values sit next to their labels; the meta-grid is for the header only):

- **Geometry** — Storage factor (severity) / Pages / Ideal / Avg row / Dead tuples % (severity), as a key/value table (`render_meta_table`). On-disk efficiency, layout, and garbage. Reuses `TableOverview` from `status:*`.
- **Visibility map** — All-visible / All-frozen rows: pages of total, severity bar, share. From `vm:*`; see below.
- **Autovacuum** — two compact `.schema-table` tables plus the Run action panel, from the self-contained `autovac:*` introspect (knobs + counters in one snapshot). Maths and wording live in `tyto/src/autovac.rs` (pure, unit-tested); `render_autovac_section` in `explorer.rs` only lays it out. See below.

**Autovacuum section.** The **Triggers** table has one row per trigger (Vacuum / Insert / Analyze / Freeze / MultiXact freeze) with columns Trigger · Measures · Current · Fires at · Progress (severity-coloured bar + %) · Rule, the rule written as PG's formula (`50 + 0.02• × 460M rows`). Formulas follow the PG 18 docs: vacuum threshold capped by `autovacuum_vacuum_max_threshold` (PG 18+), insert trigger counts `n_ins_since_vacuum` (PG 13+) and on PG 18 scales by the unfrozen fraction `1 − relallfrozen/relpages`, row basis is `pg_class.reltuples` (-1 → 0 rows, labelled "never analyzed"). Freeze rows stay live when autovacuum is off (anti-wraparound still runs); the other rows mute with the reason, and a banner names the switch (`autovacuum`, `track_counts`, or the table's `autovacuum_enabled`). Progress severity <100% green / 100–150% yellow / >150% red. The **Settings** table lists every knob by its real reloption name, grouped to mirror the triggers, with Source in plain words — `table` (reloption) / `cluster` (GUC changed from its boot default) / `default` — and a Note column when PG's rules change the value: `-1` cost settings resolve to `vacuum_cost_*`, a table `*_freeze_max_age` larger than the cluster value is ignored, `*_freeze_min_age` is limited to half and `*_freeze_table_age` to 95% of the cluster max age. Only the Progress column uses severity colour; values set on the table carry an accent dot (`•`). Partitioned parents show a note instead of the tables (autovacuum never processes them; parent stats need a manual ANALYZE). The **Run action** panel at the bottom — 4 checkboxes (Vacuum / Analyze / Freeze / Verbose) + a live SQL preview + Run — composes the statement via `compose_vacuum_sql()` and runs it in the explorer's **action shell**: its own shell tab, opened in the background next to the explorer (label `admin · <db>`, same connection + database), reused while it can take a command (live, on the database the explorer is showing, not querying, no transaction, no watch, not mid-`\password` / `\prompt` / safe-mode confirm, nothing typed), otherwise another is opened. Never a user's shell — the action shell's own session can't touch a user's open transaction, and being a shell it shows the SQL, timing, errors and VERBOSE notices. The command goes through the shell's normal submit path (`shell::run_in_shell`; a new shell runs it from `startup_sql` when its session opens). Beside Run a status line reads opening / running / done in N s / failed / "shell tab closed", derived from that shell's scrollback (`action_run_status`), with a link that brings the shell to the front (`PaneOps::focus`). When the command finishes the table's detail refreshes (`finish_explorer_action`). Run is disabled while that table's last command is still opening or running. No cancel yet: closing the action shell mid-VACUUM drops the session but the server finishes the command. MySQL section suppressed (no per-table autovac reloption surface).

The **Visibility map** section shows All-visible (severity ≥95% green / 70-95% yellow / <70% red — leading indicator for index-only-scan performance) and All-frozen (neutral — autovacuum freeze-pass workload) as rows with `N of M pages`, the shared progress bar, and a caption saying what the numbers mean and how fresh they are; a source badge reads `via pg_visibility` or `via pg_class`. The plane picks its SQL path from the session's installed extensions (`SessionOpened.extensions`, carried on `ShellTab.session_extensions` and handed to the loaders through the `ExplorerSession { id, extensions, vm_live_denied }` handle): with `pg_visibility` installed, `pg_visibility_map_summary()` gives a live read including all-frozen, and the total is the live relation size so the share can't pass 100%; otherwise `pg_class.relallvisible` (plus `relallfrozen` on PG 18+) gives the snapshot the last VACUUM / ANALYZE left. A role the server refuses `pg_visibility_map_summary()` (`insufficient_privilege`, 42501 — a non-superuser without EXECUTE on it) gets the `pg_class` read, not the permission error: Postgres checks EXECUTE when a query starts, for every function in it, so no one query can try one path and fall back to the other; a read offered `pg_visibility` goes out tagged `vmlive:` (`explorer::vm_query`), and refused, is made again from `pg_class` (`vm_read_refused`, `refire_vm`) — every such read, however many were in flight — while the session's later reads go to `pg_class` from the start (`ShellTab.vm_live_denied`, reset when a session opens); the badge's tooltip and the caption say why. Pinned by `tests/playwright/regression/storage-vm-source.spec.ts`. Partitioned parents are summed over their leaf partitions on both paths (the caption says how many). **Do not** inline-CASE-gate an extension function reference — PG resolves function names at parse time, so an untaken branch still errors on servers without the extension (PR #107); the plane branches in Rust so the name is absent from the SQL, and a unit test pins that. A failed query shows the server's error under the section header instead of hiding the section (same for Autovacuum).

Refresh: ↻ refetches every tab's data into the cached `TableDetail` in place (`refresh_table_detail`) — values stay on screen until each reply replaces them and the ↻ icon spins until the overview lands, so the tab no longer blanks or loses its scroll. DDL from a shell on the same connection refreshes the on-screen table the same way and marks every other cached table `stale`; `ensure_table_detail_loaded` refetches a stale table in place the next time it's opened. Tables-only via `show_storage_tab = kind == ObjectKind::Tables` — mirrors ERD / Data gating.

## ERD Tab (per-table)

Schema Explorer's table-detail view has an **ERD** tab alongside Schema / Storage / DDL / Data / Privileges. Renders the table's foreign-key topology as HTML cards laid out across up to five generation bands (grandparent | parent | TARGET | child | grandchild) with crow's-foot Bézier edges between them. Bands collapse left when empty. Edge anchors follow the **Pinned-Perfect / Largest-Gap** rule: an edge whose ideal y falls inside the parent card's vertical extent pins at perfection (straight line); the rest land in the largest available gap. Each source card gets its own per-card lane shift on its outgoing curves so edges from different cards in the same band gap take distinct horizontal paths.

Toolbar in the top-right of the canvas:
- **Keys only** checkbox (default checked) — when off, fires a single bulk-columns introspect query (`erdcols:focal.table` tag, `table_columns_bulk_sql`) and re-renders every card with all its columns, FK/PK rows tinted, plain rows untinted
- **Generations** dropdown — 0 / 1 / 2 hops, dynamically capped to the table's actual depth
- **Zoom** controls — `−` / `100%` / `+`. Cmd/Ctrl+scroll, trackpad pinch, and double-click on empty canvas all zoom (cursor-anchored). Double-click on a card is suppressed (cards have click-to-navigate)

Other interactions:
- **Hover focus mode**: hovering a card dims everything not directly connected to it (via opacity, no colour change)
- **Click on a non-target card's table-name header**: re-centres the inspector on that table, ERD tab still active
- **Partitions inside the focal card**: when the focal table is a partitioned root, partitions list at the bottom (capped at 8 with "+N more"); clicking a partition navigates to its detail's *Schema* tab (its ERD would mirror the parent's)
- **Empty-state hint**: "No foreign-key relationships." caption under the focal card when `max_depth_available == 0`

Implementation lives in `tyto/src/explorer.rs` (`render_erd_tab` and the `erd_*` helpers, ~1,700 lines). Per-`TableDetail` signals back the toolbar state (`erd_zoom`, `erd_generations`, `erd_keys_only`, `erd_neighbour_columns`) so each table remembers its own settings across tab switches. DDL invalidation in `tyto/src/main.rs` clears `ancestors` / `descendants` / `partitions` / `erd_neighbour_columns` and re-fires the introspect queries on every cached `TableDetail`.

Design source: `vault/Architecture/ERD_PANEL_SPEC.md` + `erd.html` reference mock. Implementation diverges in: cool palette retained (no warm-tinted migration), Arc view skipped, median-sweep ordering deferred, cards aligned via simple alphabetical-then-resolve rather than barycentric layering.

## Data Tab (per-table)

Schema Explorer's table-detail view has a **Data** tab that paginates the raw rows and supports inline CRUD via the same DBMS-agnostic plane SQL layer. The four single-statement DML primitives ship today, all keyed off the row's primary key:

- **UPDATE** (Phase 4 — UPDATE-and-go) — double-click a cell (or Enter on the keyboard cursor cell) opens an inline input. Enter / blur commits via `update_row_sql`; Esc cancels with the typed value discarded. Saved cells flash green for 1.5s; failures keep the cell red with the DB error in the title attribute.
- **INSERT** (Phase 5a) — `+` button in the data toolbar swaps the body into a vertical per-column form. One input per column with type hint; empty inputs are omitted from the INSERT so DB defaults / AUTO_INCREMENT / SERIAL fire. Typing `NULL` (uppercase) emits a bare SQL NULL keyword. Save sends `insert_row_sql`, refetches the page, briefly shows "Saved" before flipping back to Grid mode.
- **DELETE** (Phase 5b) — `−` button arms an inline red banner above the grid: "Delete row where {pk}={val}? [Cancel] [Delete]". Confirm sends `delete_row_sql`; success clears the banner and refetches. Tables without a detected PK get a disabled-state banner.
- **UPSERT** (Phase 7) — checkbox on the Insert form's toolbar. When checked, Save dispatches `upsert_row_sql` instead of `insert_row_sql`. PG: `INSERT … ON CONFLICT (pk) DO UPDATE SET non_pk_col = EXCLUDED.non_pk_col` (or `DO NOTHING` when only PK columns are filled). MySQL: `INSERT … ON DUPLICATE KEY UPDATE non_pk_col = VALUES(non_pk_col)` (or `INSERT IGNORE` for the PK-only case). Disabled when no PK is detected — without a conflict target the operation is meaningless.

Conventions shared across all four: `'value'` literals with single-quote doubling for escape; the literal string `NULL` becomes a bare `NULL` keyword; identifier quoting follows the plane's native style (backticks vs double quotes).

## Schema Explorer Keyboard Navigation

The explorer is fully keyboard-navigable as a four-layer cursor model. Mouse and keyboard write the same per-tab signals so the two never disagree.

- **Outer table list** — `↑/↓` walks the row highlight (the existing yellow-cream + blue-text "active" style, now driven by `cursor_key`). Enter on a non-loaded cursor row loads the detail; Enter again on a loaded row whose active tab is Data **or** Schema descends into that body.
- **Detail tab strip** — `←/→` activates each tab as the cursor walks. There's no separate cursor visual: the active-tab underline IS the cursor since `←/→` switches tabs as it moves.
- **Data tab body** (DataBody mode) — `↑/↓/←/→` walk a per-cell cursor (spreadsheet-style); `Tab/Shift+Tab` are synonyms for `→/←`; Enter opens the inline editor on the focused cell.
- **Schema tab body** (SchemaBody mode) — `↑/↓` walks the Columns list with the same row highlight; `←/→` exits SchemaBody and hands off to the tab strip walker.

Esc walks one level up at every layer: cell editor → cell cursor → tab strip → outer list. Esc-Esc from the outer list (within ~500ms) closes the inspector entirely.

State signals on `TableDetail`: `data_selected_row` + `data_selected_col` (DataBody cursor), `schema_selected_row` (SchemaBody cursor). Outer-list cursor is `tab.explorer_cursor_key`.

## Key Design Decisions

- **Session pinning**: each pane gets a dedicated `LiveConnection` (enum over `MySqlConnection` / `PgConnection`), never pooled. Required for temp tables, transactions, session variables.
- **Sessions as the native CLI gets them**: sqlx changes a session after connecting unless told not to. MySQL sessions open through `connect_mysql` (noctua/src/main.rs), which turns those changes off so `time_zone`, `sql_mode` (`||` is OR, not concat) and the connection collation are the server's — pinned live by `cargo test -p noctua -- --ignored mysql_session_matches_the_cli`. The patched sqlx-mysql (`vendor/`) leaves out the handshake flags the CLI doesn't send (`CLIENT_FOUND_ROWS`, `CLIENT_IGNORE_SPACE`), so UPDATEs report rows changed and `sql_mode` is the server's. Postgres sessions open through `connect_pg`: the server's own `TimeZone`, `DateStyle` and `extra_float_digits` (postgresql.conf, `ALTER ROLE` / `ALTER DATABASE ... SET`), as psql's — the patched sqlx-postgres no longer sends `TimeZone=UTC` / `DateStyle=ISO, MDY` in the startup message, and `extra_float_digits` isn't sent — so a timestamp prints, and one typed without a zone is read, in the server's zone (`2026-10-02 03:34:56.5-07`), not UTC. Pinned live by `cargo test -p noctua -- --ignored pg_session_matches_psql`. The closer to the user, the stronger: the time zone this browser chose (Settings › Time zone, sent with `Connect`) beats libpq's environment variables in noctua's environment — `PGTZ`, `PGDATESTYLE`, `PGGEQO`, read as libpq reads them (`pg_session_settings`: unset or `default` sends nothing) — which beat the server's settings, as psql's `PGTZ` does: each sent as libpq sends it, a parameter of its own in the startup message (the patched sqlx's `startup_param`, which poolers such as PgBouncer pass on, unlike `-c` in `options`), source `client`, above `ALTER ROLE` / `ALTER DATABASE`. A zone the server doesn't know refuses the session in its words (`invalid value for parameter "TimeZone": "…"`). MySQL sessions keep the server's `time_zone`.
- **Shell is one div**: the input textarea lives inline at the bottom of the scroll content, not as a fixed footer.
- **Prompt tracks history**: while browsing with arrow keys, the prompt shows the historical command number. On execute, stamps the current (next) sequence number.
- **DBMS planes** (implemented): each database type has a plane in `tyto/src/plane/` owning meta-command translations, schema-explorer SQL, keyword/function lists, and connection form defaults. Backend stays DBMS-agnostic — planes translate to SQL before sending. MySQL and Postgres ship today; see `vault/Architecture/DBMS Planes.md`.

### Design principle: no transactions across user think-time

The data-tab GUI stays single-statement, auto-commit. Multi-row / multi-table atomicity is what the **shell pane** is for — a DBA who needs `BEGIN; …; COMMIT;` types it in the shell, where they explicitly own the transaction boundary and the SQL is right in front of them. A GUI invites click → think → click → think → commit, and any feature that lets that span a transaction creates think-time inside it — the textbook long-running-transaction incident pattern, where locks are held while a user reads / deliberates / walks away. When evaluating future features, ask "does this introduce think-time inside a transaction?" — if yes, redesign or drop. (Phase 6 multi-cell pending edits was sketched and dropped on this rule.)
